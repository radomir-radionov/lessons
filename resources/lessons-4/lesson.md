## 1. Введение: зачем нужен Git

### Проблема без контроля версий

Представь, что ты делаешь сайт. Каждый день ты меняешь файлы: добавляешь стили, правишь HTML, пробуешь новые идеи. Через неделю что-то сломалось — и ты не помнишь, что именно изменил вчера. Или ты сохранил файл как `index-v2.html`, `index-final.html`, `index-FINAL-FINAL.html` — и уже не знаешь, какая версия актуальная.

**Система контроля версий (VCS)** решает эту проблему: она записывает историю всех изменений в проекте и позволяет в любой момент вернуться к предыдущей версии.

### Аналогия

Представь, что проект — это книга:

- **Файлы проекта** — страницы книги (`index.html`, `style.css`)
- **Коммит** — издание книги с датой и описанием («Добавлена шапка сайта»)
- **Git** — библиотекарь, который хранит все издания и знает, что изменилось между ними
- **GitHub** — онлайн-библиотека, где книгу могут видеть другие люди

### Git и GitHub — не одно и то же

| | Git | GitHub |
| --- | --- | --- |
| **Что это** | Программа на твоём компьютере | Сайт в интернете |
| **Где работает** | Локально, в терминале | В облаке (серверы GitHub) |
| **Зачем** | Записывать историю изменений | Хранить код онлайн, делиться, работать в команде |
| **Нужен интернет?** | Нет (для локальных коммитов) | Да (для push/pull) |

> Git работает и без GitHub. Но GitHub — самый популярный способ хранить и показывать свой код в интернете. Это как Google Drive, но специально для кода.

### Определения и понятия

#### VCS (Version Control System)

**VCS (система контроля версий)** — программа, которая отслеживает изменения в файлах проекта и сохраняет историю этих изменений.

Зачем нужна:

- **История** — можно посмотреть, что и когда менялось
- **Откат** — можно вернуться к рабочей версии, если что-то сломалось
- **Безопасность** — изменения не теряются при сбое компьютера (если код отправлен на GitHub)
- **Совместная работа** — несколько человек могут работать над одним проектом

Примеры VCS: Git (самый популярный), Mercurial, SVN.

#### Git

**Git** — распределённая система контроля версий. Создана Линусом Торвальдсом в 2005 году для разработки ядра Linux.

Ключевые особенности:

- Работает **локально** — не нужен интернет для коммитов
- Хранит **полную историю** проекта в папке `.git`
- Быстрый и надёжный — используется в крупнейших проектах мира

#### Репозиторий (repository)

**Репозиторий (repo)** — папка проекта, в которой Git отслеживает изменения. Внутри создаётся скрытая папка `.git` — там хранится вся история.

Один проект = один репозиторий. Репозиторий инициализируется командой `git init`.

#### Коммит (commit)

**Коммит** — сохранённый «снимок» (snapshot) проекта в определённый момент времени. У каждого коммита есть:

- **Уникальный идентификатор** (хеш, например `a1b2c3d`)
- **Сообщение** — краткое описание, что изменилось
- **Автор и дата** — кто и когда сделал коммит
- **Список файлов** — какие файлы вошли в этот снимок

Коммит — как точка сохранения в игре: можно вернуться к ней позже.

#### GitHub

**GitHub** — веб-сервис для хостинга Git-репозиториев. Позволяет:

- Хранить код в облаке
- Показывать проекты в портфолио
- Работать в команде (pull request, issues)
- Деплоить сайты (GitHub Pages)

Адрес: [github.com](https://github.com). Бесплатный аккаунт подходит для обучения.

## 2. Установка и настройка Git

### Шаг 1. Проверить установку

Открой терминал в VS Code: **Terminal → New Terminal** (или `` Ctrl + ` `` / `` Cmd + ` ``).

```bash
git --version
```

Если Git установлен, увидишь что-то вроде:

```
git version 2.43.0
```

Если команда не найдена — скачай Git с [git-scm.com](https://git-scm.com/) и установи. После установки **перезапусти VS Code**.

### Шаг 2. Настроить имя и email (один раз)

Git записывает автора каждого коммита. Настрой это один раз на компьютере:

```bash
git config --global user.name "Твоё Имя"
git config --global user.email "твой@email.com"
```

> Используй тот же email, что и при регистрации на GitHub — так коммиты будут привязаны к твоему профилю.

Проверить настройки:

```bash
git config --global user.name
git config --global user.email
```

### Шаг 3. Инициализировать репозиторий

Перейди в папку своего проекта (например, `my-first-site`) и выполни:

```bash
cd ~/Documents/my-first-site
git init
```

Результат:

```
Initialized empty Git repository in /Users/you/my-first-site/.git/
```

Теперь Git отслеживает эту папку. Появилась скрытая папка `.git` — **не удаляй и не редактируй её вручную**.

Проверь статус:

```bash
git status
```

В пустом репозитории увидишь:

```
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)
```

### Определения и понятия

#### Терминал (командная строка)

**Терминал** — текстовый интерфейс для ввода команд. В VS Code встроен терминал (внизу окна). Git управляется через команды в терминале.

#### `git init`

**`git init`** — команда, которая превращает обычную папку в Git-репозиторий. Создаёт скрытую папку `.git` с историей и настройками.

Выполняется **один раз** в корне проекта.

#### Папка `.git`

**Папка `.git`** — служебная директория, где Git хранит всю историю коммитов, ветки и настройки. Скрыта по умолчанию (имя начинается с точки).

- Не добавляй `.git` в `.gitignore` — Git сам её не коммитит
- Не удаляй `.git` — иначе потеряешь всю историю
- Не редактируй файлы внутри `.git` вручную

#### Ветка (branch)

**Ветка (branch)** — независимая линия разработки. По умолчанию при `git init` создаётся ветка `main` (раньше называлась `master`).

На этом уроке мы работаем только с одной веткой `main`. Ветвление — на следующих уроках.

#### `git status`

**`git status`** — команда, которая показывает текущее состояние репозитория:

- На какой ветке ты находишься
- Какие файлы изменены, но не добавлены в коммит
- Какие файлы готовы к коммиту (staged)
- Есть ли неотслеживаемые (untracked) файлы

Используй `git status` часто — это главный способ понять, что происходит с проектом.

## 3. Основной цикл Git: add, commit, status

### Три состояния файла

Каждый файл в Git-репозитории находится в одном из трёх состояний:

```
┌─────────────┐    git add     ┌─────────────┐   git commit   ┌─────────────┐
│  Modified   │ ─────────────► │   Staged    │ ─────────────► │  Committed  │
│ (изменён)   │                │ (подготовлен)│                │ (сохранён)  │
└─────────────┘                └─────────────┘                └─────────────┘
     ▲                                                              │
     └──────────────────── редактирование файла ────────────────────┘
```

1. **Modified (изменён)** — файл изменён, но Git ещё не знает, что именно сохранить
2. **Staged (подготовлен)** — файл добавлен в «корзину» для следующего коммита (`git add`)
3. **Committed (сохранён)** — файл зафиксирован в истории (`git commit`)

### Добавление файлов: `git add`

Добавить один файл:

```bash
git add index.html
```

Добавить все изменённые файлы в папке:

```bash
git add .
```

Точка `.` означает «текущая папка и всё внутри».

После `git add` проверь статус:

```bash
git status
```

Файлы в секции **Changes to be committed** (зелёные) — готовы к коммиту.

### Создание коммита: `git commit`

```bash
git commit -m "Добавлена главная страница"
```

- `-m` — message (сообщение коммита)
- Сообщение должно быть **кратким и понятным** — описывать, *что* изменилось

**Хорошие сообщения:**

- `"Добавлена главная страница"`
- `"Подключены стили CSS"`
- `"Исправлена ссылка в шапке"`

**Плохие сообщения:**

- `"fix"` — непонятно, что исправлено
- `"изменения"` — слишком общее
- `"asdfgh"` — бессмысленное

### Полный цикл: от изменения до коммита

```bash
# 1. Измени файл в редакторе и сохрани (Cmd+S / Ctrl+S)

# 2. Проверь, что изменилось
git status

# 3. Добавь файлы в staging
git add index.html style.css

# 4. Создай коммит
git commit -m "Добавлены HTML и CSS"

# 5. Убедись, что всё чисто
git status
```

После коммита `git status` покажет:

```
On branch main
nothing to commit, working tree clean
```

Это значит: все изменения сохранены в истории.

### Пример: три коммита в проекте

```bash
# Коммит 1 — начальная структура
git add index.html
git commit -m "Создана HTML-страница"

# Коммит 2 — стили
git add style.css
git commit -m "Добавлены базовые стили"

# Коммит 3 — изображения
git add images/
git commit -m "Добавлены изображения"
```

---

### Определения и понятия

#### `git add`

**`git add`** — команда, которая добавляет файлы в **staging area** (область подготовки) перед коммитом.

- `git add <файл>` — добавить конкретный файл
- `git add .` — добавить все изменения в текущей папке
- `git add *.css` — добавить все CSS-файлы

Файл в staging area готов к включению в следующий коммит.

#### Staging area (индекс)

**Staging area (область подготовки, индекс)** — промежуточная зона между рабочей папкой и историей коммитов. Сюда попадают файлы после `git add`.

Зачем нужна: можно выбрать, какие именно изменения войдут в коммит. Например, закоммитить только HTML, а CSS оставить на потом.

#### `git commit`

**`git commit`** — команда, которая создаёт новый коммит (снимок) из файлов в staging area.

```bash
git commit -m "Описание изменений"
```

Без `-m` Git откроет текстовый редактор для ввода сообщения — на первых порах используй `-m`.

#### Сообщение коммита (commit message)

**Сообщение коммита** — краткое текстовое описание того, что изменилось в этом коммите. Пиши в повелительном наклонении: «Добавить», «Исправить», «Удалить».

Правило: если через месяц ты прочитаешь сообщение — должно быть понятно, что произошло.

#### Working directory (рабочая директория)

**Working directory (рабочая директория)** — обычная папка проекта, где ты редактируешь файлы. Это то, что видишь в VS Code Explorer.

Изменения в рабочей директории не попадают в историю автоматически — нужны `git add` и `git commit`.

#### Untracked files (неотслеживаемые файлы)

**Untracked files** — файлы, которые есть в папке проекта, но Git о них ещё не знает. `git status` показывает их красным:

```
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        style.css
```

Чтобы Git начал отслеживать файл — выполни `git add`.

## 4. История изменений: `git log` и `.gitignore`

### Просмотр истории: `git log`

Посмотреть все коммиты:

```bash
git log
```

Компактный вид (рекомендуется):

```bash
git log --oneline
```

Пример вывода:

```
a1b2c3d Добавлены изображения
e4f5g6h Добавлены базовые стили
i7j8k9l Создана HTML-страница
```

Самый свежий коммит — сверху. Хеш (`a1b2c3d`) — уникальный идентификатор коммита.

Посмотреть последние 3 коммита:

```bash
git log --oneline -3
```

### Файл `.gitignore`

Не все файлы нужно хранить в Git. Некоторые файлы:

- Генерируются автоматически (кэш, сборка)
- Специфичны для твоего компьютера (`.DS_Store` на Mac)
- Содержат секреты (пароли, ключи API)

Для этого существует файл **`.gitignore`** — список файлов и папок, которые Git **игнорирует**.

Создай файл `.gitignore` в корне проекта:

```gitignore
# Системные файлы macOS
.DS_Store

# Системные файлы Windows
Thumbs.db
desktop.ini

# Папки редакторов
.vscode/
.idea/

# Зависимости (на будущее)
node_modules/

# Временные файлы
*.log
*.tmp
```

После создания `.gitignore`:

```bash
git add .gitignore
git commit -m "Добавлен .gitignore"
```

> Файлы, уже закоммиченные до добавления в `.gitignore`, останутся в истории. Чтобы убрать: `git rm --cached <файл>`.

### Типичный `.gitignore` для HTML/CSS-проекта

```gitignore
.DS_Store
Thumbs.db
*.log
.vscode/
```

Этого достаточно для начала. По мере роста проекта список можно расширять.

### Определения и понятия

#### `git log`

**`git log`** — команда для просмотра истории коммитов в текущей ветке.

Полезные флаги:

| Команда | Что делает |
| --- | --- |
| `git log` | Полная информация (автор, дата, сообщение) |
| `git log --oneline` | Одна строка на коммит |
| `git log -3` | Последние 3 коммита |
| `git log --oneline -5` | Последние 5 коммитов в компактном виде |

#### Хеш коммита (commit hash)

**Хеш коммита** — уникальный идентификатор коммита, например `a1b2c3d4e5f6`. Генерируется автоматически Git на основе содержимого коммита.

Обычно достаточно первых 7 символов для идентификации.

#### `.gitignore`

**`.gitignore`** — текстовый файл в корне репозитория, который указывает Git, какие файлы и папки **не отслеживать**.

Синтаксис:

| Паттерн | Значение |
| --- | --- |
| `file.txt` | Конкретный файл |
| `*.log` | Все файлы с расширением `.log` |
| `folder/` | Вся папка |
| `# комментарий` | Комментарий (игнорируется) |

#### Игнорируемые файлы

**Игнорируемые файлы** — файлы, которые Git видит в папке, но не предлагает добавить в коммит. Они не попадают в `git status` как untracked.

## 5. GitHub: удалённый репозиторий и push

### Зачем выкладывать код на GitHub

- **Портфолио** — работодатели и преподаватели видят твои проекты
- **Резервная копия** — код не потеряется, если сломается компьютер
- **Доступ с любого устройства** — можно клонировать проект на другой ПК
- **Совместная работа** — другие разработчики могут вносить изменения

### Шаг 1. Создать аккаунт на GitHub

1. Перейти на [github.com](https://github.com)
2. Нажать **Sign up** и зарегистрироваться
3. Подтвердить email

### Шаг 2. Создать новый репозиторий

1. Нажать **+** → **New repository**
2. Заполнить:
   - **Repository name:** `my-first-site` (или имя своего проекта)
   - **Description:** краткое описание (необязательно)
   - **Public** — код виден всем (для портфолио)
   - **НЕ** ставить галочки «Add a README», «Add .gitignore» — у нас уже есть локальный проект
3. Нажать **Create repository**

GitHub покажет инструкции. Нам нужен блок **«…or push an existing repository from the command line»**.

### Шаг 3. Подключить удалённый репозиторий

Скопируй URL репозитория (кнопка **Code** на GitHub):

```
https://github.com/твой-username/my-first-site.git
```

В терминале, в папке проекта:

```bash
git remote add origin https://github.com/твой-username/my-first-site.git
```

- `remote` — удалённый репозиторий
- `origin` — стандартное имя для основного удалённого репозитория
- URL — адрес репозитория на GitHub

Проверить:

```bash
git remote -v
```

Вывод:

```
origin  https://github.com/твой-username/my-first-site.git (fetch)
origin  https://github.com/твой-username/my-first-site.git (push)
```

### Шаг 4. Отправить код: `git push`

```bash
git push -u origin main
```

- `push` — отправить коммиты на удалённый сервер
- `-u` — запомнить связь (при следующих push достаточно `git push`)
- `origin` — имя удалённого репозитория
- `main` — имя ветки

При первом push GitHub может попросить авторизацию:

- **Логин** — твой username на GitHub
- **Пароль** — Personal Access Token (не обычный пароль от аккаунта)

> Если терминал просит пароль — создай Personal Access Token в GitHub: Settings → Developer settings → Personal access tokens → Generate new token. Скопируй токен и вставь вместо пароля.

После успешного push обнови страницу репозитория на GitHub — там появятся все файлы проекта.

### Полная последовательность (шпаргалка)

```bash
# Локально
git init
git add .
git commit -m "Первый коммит"

# Подключение к GitHub
git remote add origin https://github.com/username/repo.git
git push -u origin main

# При следующих изменениях
git add .
git commit -m "Описание изменений"
git push
```

---

### Определения и понятия

#### Удалённый репозиторий (remote)

**Удалённый репозиторий (remote)** — копия репозитория, хранящаяся на другом сервере (например, GitHub). Связывается с локальным через `git remote add`.

Стандартное имя основного remote — `origin`.

#### `git remote`

**`git remote`** — команда для управления удалёнными репозиториями.

| Команда | Что делает |
| --- | --- |
| `git remote add origin <url>` | Подключить удалённый репозиторий |
| `git remote -v` | Показать список remote с URL |
| `git remote remove origin` | Отключить remote |

#### `git push`

**`git push`** — команда, которая отправляет локальные коммиты на удалённый репозиторий.

```bash
git push -u origin main   # первый раз (с запоминанием)
git push                  # последующие разы
```

Без `push` коммиты остаются только на твоём компьютере.

#### `origin`

**`origin`** — стандартное имя (псевдоним) для основного удалённого репозитория. Это не команда, а имя, которое ты задаёшь при `git remote add origin <url>`.

#### `main`

**`main`** — имя основной ветки в современных репозиториях. Раньше использовалось имя `master`. Проверить имя своей ветки: `git branch`.

#### Personal Access Token (PAT)

**Personal Access Token (PAT)** — специальный ключ для авторизации в GitHub из терминала. Обычный пароль от аккаунта GitHub для `git push` не работает — нужен токен.

Создаётся в: GitHub → Settings → Developer settings → Personal access tokens.

#### URL репозитория

**URL репозитория** — адрес репозитория на GitHub. Два формата:

- HTTPS: `https://github.com/username/repo.git` — проще для начала
- SSH: `git@github.com:username/repo.git` — требует настройки SSH-ключа

На этом уроке используем HTTPS.

## Словарь терминов

| Термин | Краткое определение |
| --- | --- |
| VCS | Система контроля версий — отслеживает историю изменений |
| Git | Распределённая система контроля версий |
| GitHub | Веб-сервис для хостинга Git-репозиториев |
| Репозиторий (repo) | Папка проекта с историей Git (папка `.git`) |
| Коммит (commit) | Сохранённый снимок проекта с сообщением |
| Ветка (branch) | Независимая линия разработки (`main`) |
| `git init` | Инициализация репозитория в папке |
| `git add` | Добавление файлов в staging area |
| `git commit` | Создание коммита из подготовленных файлов |
| `git status` | Просмотр текущего состояния репозитория |
| `git log` | Просмотр истории коммитов |
| Staging area | Область подготовки файлов перед коммитом |
| Working directory | Рабочая папка с файлами проекта |
| Untracked | Файл, который Git ещё не отслеживает |
| `.gitignore` | Список файлов, игнорируемых Git |
| Remote (origin) | Удалённый репозиторий на сервере |
| `git remote` | Управление удалёнными репозиториями |
| `git push` | Отправка коммитов на удалённый сервер |
| Хеш коммита | Уникальный идентификатор коммита |
| PAT | Personal Access Token — ключ для авторизации в GitHub |
| `main` | Имя основной ветки репозитория |
